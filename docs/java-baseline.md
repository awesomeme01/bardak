из этого файла — не по памяти и не по документации, а прогоном.

## Как воспроизвести

```sh
docker compose up -d                                   # Postgres 16

cd back-bardak
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew clean check --no-daemon
```

⚠️ `--no-daemon` не косметика: демон Gradle в этом проекте однажды остановил запущенный
рядом `bootRun`. Если сервер поднят для ручной проверки — прогонять только так.

Запуск сервера для ручных проверок и smoke-тестов:

```sh
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew bootRun      # :8088
```

### Почему 380 прогонов при 351 аннотации

В коде **351** метод с `@Test` плюс **6** `@ParameterizedTest`. Параметризованные
разворачиваются в несколько прогонов каждый, отсюда 380. `@RepeatedTest` и `@TestFactory`
не используются.

Для матрицы миграции единицей учёта берётся **метод исходника** (351 + 6 = 357 строк),
а не прогон: параметризованный тест переносится одним табличным тестом Go.

Файлы с `@ParameterizedTest`: `MatchStateCodecTest`, `DeckFactoryTest`,
`CardRankMatchingTest`, `DealerTest`, `TrumpTest` (+ один в том же наборе).

## Разделение юнит/интеграция

Интеграционные помечены `@Tag("integration")` и вынесены в отдельную задачу Gradle
`integrationTest`; `test` их не запускает. Классов с тегом — **18**.

Интеграционные поднимают настоящий Postgres через Testcontainers.

## Нестабильные тесты

**На момент фиксации нестабильных нет** — прогон чистый, пропусков нет, отключённых нет.

Исторически нестабильность была одна, и она вылечена:

> `DealHistoryIT` падал плавающе. Причина оказалась не в тесте: каждый интеграционный
> класс поднимал свой контейнер Postgres, пятнадцать одновременных исчерпывали память
> Docker. Лечение — singleton-контейнер `TestPostgres` (`src/test/java/kz/bardak/TestPostgres.java`),
> общий на весь прогон. Заодно время интеграционных упало с ~70 с до ~40 с.

Это важно для Go: Testcontainers for Go нужно настраивать так же — один контейнер на
пакет тестов, а не на класс.

## Что считается «поведением baseline»

При расхождении Go и Java источником истины считается **код Java на зафиксированном
коммите**, а не проектная документация: `planning/*.md` местами отстаёт от кода, и
расхождения отмечаются отдельно в контрактных документах.

Исключение — случаи, где Java-поведение признано ошибкой и уже исправлено в этом же
коммите (например, 404 вместо 500 на неизвестный путь). Такие места помечены в
`docs/rest-contract.md`.
