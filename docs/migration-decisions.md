# Решения по миграции Java → Go

Каждое решение — с причиной. Требования велят не задавать вопросов по техническим
деталям, а решать и фиксировать; это тот самый файл.

Порядок: новые сверху.

## MD-005 — Go не воспроизводит `java.util.Random` побитово

**Дата:** 2026-08-19 · **Проверено чтением кода восстановления**

**Решение:** Go тасует колоду своим генератором. Требуется детерминизм **внутри Go**
(один seed → одна колода), но НЕ побитовое совпадение с Java.

**Причина — что было бы иначе:** Java тасует через `Collections.shuffle(cards,
new Random(seed))`. Это конкретный LCG со своим порядком выборки; повторить его в Go
можно только переписав `java.util.Random` и алгоритм `shuffle` вручную. Это код,
который никто никогда не прочитает, но который обязан быть верным до последнего бита.

**Почему это безопасно — три факта из кода, а не рассуждение:**

1. Восстановление матча после перезапуска (`MatchService.restore`) декодирует **полный
   снимок состояния** (`stateCodec.decode(snapshot.state())`) и НЕ проигрывает события
   заново. Карты берутся из снимка, а не пересдаются из seed.
2. Снимок сохраняется **после каждого хода** (`saveSnapshot` в `GameCommandHandler`),
   поэтому он никогда не отстаёт настолько, чтобы понадобилось доигрывание.
3. Реплей (`MatchHistoryService.replay`) читает записанные `match_events`, а не
   пересчитывает партию из seed.

Следствие: **передача матча между бэкендами на середине партии работает** — Go поднимет
идущий матч Java из снимка с теми же картами. Это и есть требование совместимости данных;
совпадение колод из одинакового seed для него не нужно.

**Цена:** differential-тест не может сравнивать карты в раздаче, начатой каждым бэкендом
самостоятельно. Это предусмотрено требованиями (§11.3 прямо разрешает нормализовать
«random deck»): сравниваются структура событий, порядок, коды ответов и переходы
состояний, а не конкретные карты.

**Что обязано сохраниться:** источник случайности передаётся параметром, а не берётся
глобально. Иначе тест не воспроизвести, а «плавающий» баг правил не поймать.

## MD-004 — Схемой владеет Flyway, Go в неё не мигрирует

**Дата:** 2026-08-19

**Решение:** в окне отката Go **не накатывает миграции**. Схему создаёт и обновляет
Flyway из Java-бэкенда; `goose` в `back-go/migrations/` заводится, но остаётся пустым
до самого cutover.

**Причина:** обе версии работают с одной базой. Два мигратора на одну схему — это две
служебные таблицы (`flyway_schema_history` и `goose_db_version`), каждая со своим
представлением о том, что уже накатано. Первое же расхождение чинится руками в проде.

**Следствие:** healthcheck Go читает `flyway_schema_history` — чужую служебную таблицу,
сознательно. Иначе `GET /api/health` двух бэкендов отвечал бы разным числом миграций,
а по этой ручке смотрят и люди, и `tools/smoke/run.sh`.

## MD-003 — `omitempty` в Go запрещён для полей, которые Java отдаёт всегда

**Дата:** 2026-08-19 · **Важность:** ломает parity молча

**Решение:** nullable-поля в Go — **указатели** с `omitempty`; поля, которые Java отдаёт
всегда, — обычные значения **без** `omitempty`.

**Причина:** правила вырезания в Java и Go совпадают только на первый взгляд.

| | вырезает |
|---|---|
| Jackson `non_null` (глобально в `application.yml`) | только `null` |
| Go `encoding/json` + `omitempty` | `null`, `0`, `false`, `""`, пустой список |

То есть Java отдаёт `{"matches":0,"wins":0}`, а наивный Go с `omitempty` — `{}`.
Ни один тип не поменяется, компилятор промолчит, а фронт получит отсутствующее поле
там, где ждал ноль.

**Обратный случай тоже есть:** `PlayerStats.empty()` в Java вырезает `avgPlace`,
`bestRating`, `worstRating` (они `null`), но **оставляет** `"degrees": []` — пустой
список не `null`. В Go это `[]T{}` без `omitempty`, а не `nil`: `nil`-слайс
сериализуется в `null`, чего Java здесь не отдаёт никогда.

**Исключение:** `ApiError` помечен `NON_EMPTY`, а не `non_null` — у него пустая карта
`details` и пустая строка тоже вырезаются. Обычная ошибка на проводе — ровно
`{"code","message","traceId"}`.

**Как проверяется:** golden-фикстуры снимаются с Java и сравниваются побайтно после
нормализации только динамического (id, время, колода).

## MD-002 — Типы UUID в DTO повторяются по списку, а не «все одинаково»

**Дата:** 2026-08-19

**Решение:** в Go-структурах тип поля с идентификатором выбирается по тому, как его
объявил Java, а не единым правилом.

**Причина:** в Java это непоследовательно. Часть DTO отдаёт `String`
(`UserView.id`, `TableView.id`/`hostUserId`/`cardSetId`/`themeId`, `SeatView.userId`,
`FriendDtos.Friend.userId`, `CardSetView.id`, `TableThemeView.id`, `CardSetManifest.id`),
часть — нативный `UUID` (`RatingDtos.*`, `HistoryDtos.*`).

На проводе разницы нет: обе стороны — строка в каноническом нижнем регистре. Но
«причесать» это в Go — значит внести изменение, которого никто не просил, и потерять
возможность сказать «отличий нет». Причёсывание откладывается до момента, когда Java
уже не нужна.

## MD-001 — Пакет `internal/domain/game` без внешних зависимостей

**Дата:** 2026-08-19

**Решение:** правила игры не импортируют ничего, кроме стандартной библиотеки.
Закрытость иерархии карт (`sealed interface` в Java) держится неэкспортируемым
методом `sealed()`.

**Причина:** в Java эта граница уже проведена — в `game/rules/` **ноль** импортов
Spring, JPA и сети. Ослабить её при переносе значило бы потерять главное свойство
движка: он проверяется без сети и базы, за миллисекунды, и правила игры — единственное,
что нельзя починить в проде на живую.

Источник случайности передаётся параметром, а не берётся глобально: одинаковый seed
обязан давать ту же сдачу, иначе матч не воспроизвести из лога.

## Отложено за пределы этого захода (этапы 8–9)

По решению владельца делаются этапы 1–7. Вне объёма и **не забыто**:

- production-пакет: `Dockerfile`, `compose.yaml`, `Caddyfile`, скрипты deploy/rollback;
- backup и restore PostgreSQL во внешнее S3 плюс restore drill (раздел 12 требований);
- проверка на чистой Ubuntu VM 2 vCPU / 2 ГБ;
- сам cutover и наблюдение за ним.

Нагрузочная цель «2 vCPU / 2 ГБ» на этапе 7 проверяется лимитами Docker. Это **не то же
самое**, что настоящая VPS, и в отчёте будет записано именно так.
