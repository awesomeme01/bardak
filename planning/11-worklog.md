## 2026-08-06 — Уточнение правил: бардак это матч, а не партия ⭐

**Этап:** M0

**Сделано:** получены ответы автора по правилам, документы существенно переработаны.

**Главное изменение — структура игры.** Выяснилось, что «бардак» это **матч из нескольких
раздач**: карты кончились → перераздача, счёт игроков переносится дальше, навесы начисляют
очки, матч идёт до предельного счёта. Это не деталь, а изменение доменной модели:

- введены две сущности: `Match` (матч) и `Deal` (раздача), два вложенных автомата;
- в БД: `matches` / `deals` / `deal_results`, лог переименован в `match_events`;
- `seq` событий сквозной по матчу, а не по раздаче — у клиента один счётчик, переход между
  раздачами не требует особой обработки при ресинке;
- seed матча порождает под-seed каждой раздачи — весь матч воспроизводим целиком;
- рейтинг считается **по матчу**, отдельные раздачи на него не влияют;
- ADR-012.

**Закрыты вопросы:**

- **OQ-8** (порядок подкидывания) → ADR-013, ADR-014. Подтверждено: подкидывает только
  начавший раунд; закончив, жмёт **«Пас»**; право уходит **второму соседу** — следующему по
  часовой за защищающимся; назад не возвращается. Пас — явная фиксация «больше не подкидываю»,
  раунд сам по себе не завершается. Введена универсальная команда `PLAY_CARD`, где
  защищающийся **обязан** указывать целевую карту.
- **OQ-6** (выход игрока) → ADR-015. Отключение → `PAUSED` с **остановкой таймера хода**,
  60 секунд на возврат, иначе матч `ABORTED` с причиной: лог сохраняется, рейтинг не трогается.
  Таймаут хода — 30 с.

**Новые правила:** лимиты атакующих карт 5 (пока нет отбитых) / 6 (после первой отбитой);
все игровые числа вынесены в `rules_config` — в коде движка литералов быть не должно (ADR-016).

**Остановились на:** документы приведены в соответствие. Следующий шаг — **M1** (Gradle +
Spring Boot + Postgres + `/api/health` + WS-эхо + Vite-скелет). M1 ни одним открытым вопросом
не блокируется.

**Всплыло:**
- **OQ-1 понижен в приоритете.** Короткая колода при 5 игроках оказалась не проблемой:
  «карты кончились» — это штатное завершение раздачи, а не вырождение партии.
- **Новый OQ-11:** тип проигрыша определяется по итоговому состоянию стола — какие бывают
  типы и по какому признаку различаются, неизвестно. Блокирует M5.
- **Новый OQ-12:** нужна проверка формулировки лимитов 5/6.
- **Навесы (OQ-3) выросли в приоритете.** Раньше выглядели как дополнительная механика
  раунда; теперь ясно, что это **двигатель матча** — без них счёт не растёт и матч не может
  закончиться штатно. До их описания игра не собирается целиком.
- `scoreLimit` пока заглушка (100): осмысленное значение можно выбрать только зная, сколько
  очков дают навесы (OQ-13).

## 2026-08-06 — M0: репозиторий и проектная документация

**Этап:** M0

**Сделано:**
- Создан репозиторий `bardak` со структурой `back-bardak` / `front-bardak` / `planning`.
- Написаны 12 planning-документов: обзор, карта знаний, архитектура, правила игры, схема БД,
  контракты API, система дизайна карт, рейтинг, роадмап, ADR-журнал, открытые вопросы,
  этот журнал.
- Зафиксированы ключевые архитектурные решения (ADR-001…011), в том числе: сырой WS вместо
  STOMP, серверный авторитет, event sourcing, актор-модель стола, отделение дизайна карт
  от логики.
- Кода нет — это осознанно.

**Остановились на:** ждём ответов по открытым вопросам, блокирующим ближайшие этапы:
**OQ-1** (размер колоды при 5 игроках), **OQ-6** (выход игрока посреди партии),
**OQ-8** (подтверждение формализации порядка подкидывания).
Следующий шаг — **M1**: Gradle + Spring Boot + Postgres в compose + `/api/health` + WS-эхо
+ Vite-скелет фронта. M1 ни одним из этих вопросов не блокируется, можно начинать
параллельно с их обсуждением.

**Всплыло:**
- Правила бардака описаны не полностью: механика «навесов» отсутствует (OQ-3), правила
  джокеров черновые (OQ-2). Движок с самого начала проектируется под сменяемые правила
  (`AttackOrderPolicy`, `rules_config`, зарезервированная подфаза в FSM) — иначе дописывать
  их потом придётся по всему коду.
- Обнаружена арифметическая проблема с колодой: 36 карт на 5 игроков оставляют в колоде
  всего 11 карт после раздачи. Вынесено в OQ-1 как блокирующее.
- Авторизация WebSocket оказалась отдельной задачей, а не следствием REST-авторизации:
  браузерный WS не позволяет задать заголовок `Authorization`. Решено одноразовым тикетом
  (ADR-005).
