# 07 — Система рейтинга

## Единица рейтинга — матч, а не раздача ⭐

«Бардак» состоит из нескольких раздач со сквозной шкалой навесов (`03-domain-rules.md` §0).
Рейтинг считается **один раз, по итогам матча** — когда кому-то навесили джокер.
Отдельные раздачи на рейтинг не влияют вообще.

Это удачно с точки зрения статистики: матч из нескольких раздач сам по себе усредняет
везение с картами, поэтому его результат — более надёжный сигнал о силе игрока, чем исход
одной партии в дурака.

**Отменённые матчи (`ABORTED`) рейтинг не затрагивают.** Игрок ушёл — матч сохраняется для
просмотра, но `rating_*` остаются `null` и строк в `rating_history` не появляется.

## В чём сложность ⭐

Классический Elo придуман для шахмат: **два** игрока, исход бинарный (победа/ничья/поражение).
У нас матч на **2–5 игроков**, и его результат — не победа одного, а **ранжирование**:
кто как расположился по уровню навесов, и кому навесили джокер.

Применить Elo напрямую нельзя. Это главное содержательное решение в этой части проекта.

Дополнительная особенность дурака: в нём сильна роль карт. Слабый игрок с хорошей раздачей
регулярно обыгрывает сильного. Значит рейтинг должен меняться медленно и сходиться на
дистанции, а не прыгать после каждого матча.

## Варианты

### 1. Elo с попарным разложением ✅ выбран для MVP

Матч на N игроков разбирается на `C(N,2)` попарных сравнений: для каждой пары игрок с лучшим
итоговым местом «выиграл» у игрока с худшим. Места определяются по уровню навесов на конец
матча; получивший джокер — последний.

```
Для каждой пары (i, j):
    Expected_i = 1 / (1 + 10^((R_j - R_i) / 400))
    Actual_i   = 1 если place_i < place_j, иначе 0
    Δ_i       += K * (Actual_i - Expected_i)

Итог: R_i_new = R_i + Δ_i / (N - 1)      // нормировка на число пар
```

`K` зависит от опыта: 40 для первых 20 матчей, 20 после, 10 для рейтинга выше 2200.
Деление на `(N-1)` обязательно — иначе за матч на 5 игроков рейтинг гуляет вчетверо
сильнее, чем за матч на 2.

Возможное уточнение на будущее: учитывать **разрыв по шкале** — проиграть при своём уровне
`K` у соперника и при его `6` это разные вещи. Плюс **степень проигрыша** (OQ-11), которая
и задумана как мера «насколько плохо». Пока не делаем: сначала нужно увидеть, как шкала
ведёт себя в реальных партиях.

**Плюсы:** понятно, легко объяснить игрокам, легко отладить, 30 строк кода.
**Минусы:** не учитывает неопределённость рейтинга новичка; все пары считаются одинаково
важными, хотя «1-е против 5-го» и «2-е против 3-го» — разные по информативности исходы.

### 2. Glicko-2

Добавляет к рейтингу **отклонение** (RD, насколько мы уверены) и **волатильность**.
Рейтинг новичка меняется быстро, устоявшийся — медленно. RD растёт при простое.

Для N игроков применяется так же попарно, но с учётом RD соперников.

**Плюсы:** честнее к новичкам и к вернувшимся после перерыва.
**Минусы:** формулы заметно сложнее, требует понимания; выигрыш заметен на больших выборках.

### 3. TrueSkill / OpenSkill (Weng–Lin)

Спроектированы именно под ранжирование N участников. Рейтинг — распределение `(μ, σ)`,
обновляется байесовски по итоговым местам сразу, без разложения на пары.

**Плюсы:** математически самый правильный ответ для нашей задачи; быстро сходится.
**Минусы:** TrueSkill запатентован Microsoft (OpenSkill — свободная альтернатива);
для игры на десяток друзей — избыточно; результат сложнее объяснить игроку.

## Решение

**MVP: Elo с попарным разложением.** Причина — соотношение сложности и пользы: на выборке в
несколько десятков игроков разница между Elo и OpenSkill незаметна, а отлаживать простую
формулу можно за вечер.

**Но схема БД заводится сразу под более сложные модели** (см. `04-db-schema.md`):

```sql
user_rating (
    rating      numeric,   -- Elo использует это
    deviation   numeric,   -- Glicko-2 RD / OpenSkill σ — пишем 350 и не трогаем
    volatility  numeric    -- Glicko-2 — пишем 0.06 и не трогаем
)
```

Смысл: переезд на Glicko-2 или OpenSkill не потребует миграции с потерей истории. Колонки
стоят ноль, а их отсутствие потом стоит переписывания расчёта задним числом по всей
`rating_history`.

## Параметры

| Параметр | Значение | Комментарий |
|---|---|---|
| Стартовый рейтинг | 1000 | |
| `K` (первые 20 матчей) | 40 | Новичок быстро находит свой уровень |
| `K` (обычный) | 20 | |
| `K` (рейтинг > 2200) | 10 | |
| Минимум матчей для отображения в топе | 10 | Защита от «сыграл один, выиграл, я первый» |
| Нижняя граница рейтинга | 100 | Чтобы не уходить в минус |

## Хранение и пересчёт

Пересчёт выполняется **один раз, при завершении матча**, в **той же транзакции**, что и
запись результата:

```
MATCH_OVER
  → BEGIN
      matches.status = FINISHED, finished_at, loser_user_id, loss_type
      match_players.place, naves_level, rating_before, rating_after, rating_delta
      user_rating: обновление rating, matches_played
      rating_history: строка на каждого участника
    COMMIT
  → событие MATCH_OVER клиентам с ratingChanges[]
```

Одна транзакция — потому что «матч записался, а рейтинг нет» даёт неисправимое расхождение
между историей и текущим рейтингом.

**При `MATCH_ABORTED` ничего из этого не выполняется** — пишется только статус и причина.

`rating_history` хранит `rating_before`/`rating_after` каждого матча. Это даёт:
- график рейтинга в профиле;
- возможность разобраться, почему рейтинг такой;
- возможность **пересчитать всё с нуля** по истории, если формула изменится.

Последнее — главная причина хранить историю подробно. Переход Elo → Glicko-2 выполняется
пересчётом всех матчей в хронологическом порядке.

## Защита от накрутки (не MVP, но продумано)

Игра на друзей, поэтому сговор реален и тривиален: двое играют друг с другом, один
намеренно проигрывает.

Меры по возрастанию строгости:
1. Минимум матчей для попадания в рейтинг-лист.
2. Затухающий вес за повторные матчи с тем же соперником в короткий срок.
3. Игнорировать подозрительно короткие матчи (джокер за одну-две раздачи).
4. Разделить «рейтинговые» и «дружеские» столы — флаг на столе.

Отдельный вектор, специфичный для нашей модели: **намеренный выход из матча ради отмены**,
когда проигрыш уже неизбежен. Сейчас это работает и ничем не наказывается. Если станет
проблемой — считать выходящему техническое поражение вместо отмены (см. OQ-6, решение
сознательно отложено).

На MVP не делаем ничего из этого, но пункт 4 стоит заложить в `rules_config` заранее.

## Что показываем игроку

- Текущий рейтинг и позицию в топе (при ≥10 матчах).
- Дельту за последний матч, сразу в экране результата.
- График рейтинга за период (из `rating_history`).
- Число матчей и распределение мест.
- Отменённые матчи — отдельно, с пометкой «не учитывается».

## Сезоны ✅ (ADR-037)

Рейтинг **сезонный**, но сезоны не привязаны к календарю: сезон — строка в таблице `seasons`
с датами начала и конца, закрывает его админ, когда за столом накопилось достаточно партий.
Рейтинг считается внутри сезона, `rating_history` остаётся сквозной. Итоговые таблицы
прошлых сезонов доступны только на чтение.

## Открытые вопросы
- Учитывать ли разрыв по шкале навесов, а не только места?
- Считать ли рейтинг на столах с нестандартными правилами (навесы включены/выключены,
  укороченная `naves.scale`) вместе или раздельно? Матч по шкале из четырёх ступеней и по
  полной — разные по длине события.
- Влияет ли **тип проигрыша** (OQ-11) на величину рейтинговой потери?
