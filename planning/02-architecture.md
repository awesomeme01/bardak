## Модули

| Модуль | Ответственность |
|---|---|
| `auth` | Регистрация, логин, JWT access/refresh, выдача WS-тикета |
| `user` | Профиль, отображаемое имя, аватар |
| `lobby` | Столы: создание, список, join/leave/ready, старт партии |
| `game.engine` | **Чистая игровая логика.** Автомат матча + автомат раздачи, команды, правила, счёт. Без Spring, БД и сети |
| `game.runtime` | Реестр активных столов, очередь команд на стол, таймеры хода, пауза при отключении, вызов engine, публикация событий |
| `game.ws` | WebSocket-хендлеры, разбор конвертов, персональные проекции состояния, рассылка |
| `history` | Персист лога событий, снапшоты, выдача истории и реплея |
| `rating` | Расчёт рейтинга по итогам **матча**, история рейтинга |
| `assets` | Наборы карт, темы стола, манифесты |

## Правило разделения REST и WS

| | REST | WebSocket |
|---|---|---|
| **Что** | Всё, что не является ходом в живом матче | Матч и live-события |
| **Примеры** | Регистрация, логин, профиль, список столов, создание стола, история матчей, реплей, каталог наборов карт | Присоединение к столу, готовность, ход, пас, взятие, перевод, счёт, пауза, синхронизация состояния, уведомление «твой ход» |
| **Модель** | Запрос → ответ | Команда → событие(я) всем участникам стола |

Граничный случай: **создание стола идёт по REST** (это не realtime-действие), а вход за стол —
по WS, потому что с него начинается подписка на события.

## Серверный авторитет

Единственный допустимый поток:

```
клиент → COMMAND (намерение) → сервер валидирует → engine применяет
                                       ↓
                        событие в лог + EVENT всем участникам
```

Клиент **никогда** не сообщает результат — только намерение. `PLAY_CARD {cardCode,
targetCardCode}` означает «хочу отбить эту карту вот этой», а не «я отбился». Решает сервер.

Фронт может мгновенно откатить заведомо неверное действие ради отзывчивости, но это ускорение
реакции, а не источник истины: сервер валидирует ход независимо и всегда.

Список разрешённых действий сервер присылает вместе с состоянием (`availableActions`) —
чтобы фронт мог подсветить возможные ходы, не зная правил.

## Модель стола в рантайме ⭐

Ключевое решение. Стол — актороподобная сущность:

```
TableRuntime
├── tableId
├── состояние матча + текущей раздачи (в памяти, immutable, заменяется целиком)
├── очередь команд (MPSC)
├── один поток-обработчик (single-thread executor)
├── таймер текущего хода (30 с) — приостанавливаемый
└── таймер ожидания отключившегося (60 с)
```

Обработка команды:

1. Команда из WS попадает **в очередь**, а не выполняется на потоке WS-соединения.
2. Поток стола берёт команду, вызывает `engine.apply(state, command)` → `(newState, events)`.
3. События пишутся в `match_events` (append-only).
4. Для каждого участника строится **персональная проекция** и отправляется в его сокет.
5. Перезапускается таймер хода.

Таймеры принадлежат рантайму, а не движку: движок обязан оставаться детерминированным и не
знать про время. Истёкший таймер приходит в него обычной командой `GAME_TIMEOUT`.

Почему так, а не блокировки вокруг разделяемого состояния: у стола 5 источников команд плюс
таймер, и каждая команда меняет состояние целиком. Очередь даёт линейный порядок бесплатно и
исключает целый класс гонок и дедлоков. Дополнительный бонус — движок может оставаться чисто
однопоточным и не думать о синхронизации вообще.

Реестр столов: `ConcurrentHashMap<TableId, TableRuntime>`. Пустые/завершённые столы выгружаются.

## Персональная проекция состояния (fog of war) ⭐

Внутреннее состояние содержит все карты всех игроков. Наружу оно **не сериализуется никогда**.

```
MatchState (полное, только на сервере: счёт матча + состояние раздачи со всеми руками)
   ↓ project(state, forPlayer)
PlayerView: своя рука целиком, у остальных — только количество карт,
            счёт всех, размер колоды, козырь, стол, чья очередь, доступные действия
```

Проекция — обязательный слой, а не фильтр в сериализаторе. Правило: если DTO может физически
содержать чужую карту, он спроектирован неправильно.

То же касается отклонённых попыток хода: наружу уходит только `{seatNo}`, остальные видят
рубашку. Какая именно карта — не покидает сервер.

## Восстановление и живучесть

| Сценарий | Поведение |
|---|---|
| Игрок потерял связь | ⭐ Матч переходит в `PAUSED`, **таймер хода замирает**. Остальные видят «Игрок 3 не может подключиться». Вернулся в течение 60 с → `MATCH_RESUMED`, таймер продолжается с остатка |
| Игрок не вернулся за 60 с | Матч `ABORTED` с причиной. Лог сохраняется целиком, **рейтинг не пересчитывается** |
| Игрок закрыл вкладку | Web Push «твой ход». Дальше — та же логика паузы и отмены |
| Рестарт бэкенда | Стол пересоздаётся из `match_events` (+ последнего снапшота). Активные матчи не теряются |
| Событие записалось, но не разослалось | Клиент обнаружит дыру в `seq` и запросит `RESYNC` |

Пауза, а не продолжение отсчёта — принципиально: иначе за время разрыва у игрока сгорит ход,
и он вернётся уже наказанным за проблемы со связью.

Порядок «сначала записать событие, потом разослать» обязателен: разослать и упасть до записи —
значит рассинхронизировать клиентов с сервером навсегда.

## Путь к нескольким параллельным столам и инстансам

**Сейчас:** несколько столов на одном инстансе работают из коробки — реестр в памяти, у каждого
стола своя очередь и свой поток. Никаких дополнительных решений не требуется.

**Когда понадобится второй инстанс** (M8, не раньше):

- Sticky routing по `table_id` — все соединения одного стола попадают на один инстанс.
  Стол остаётся однопоточным, модель не меняется.
- Redis pub/sub — для событий, выходящих за пределы стола (presence, лобби, уведомления).
- Redis-блокировка на «владение» столом, чтобы два инстанса не подняли один стол из лога.

Что делаем уже сейчас, чтобы это осталось возможным:

1. Никакого состояния в HTTP-сессии — только JWT.
2. Всё состояние матча восстановимо из `match_events`.
3. `table_id` присутствует в каждом WS-сообщении — есть по чему маршрутизировать.
4. Лобби не держит состояние в памяти — читает из БД.

## Два уровня состояния: матч и раздача ⭐

«Бардак» — это матч из нескольких раздач со сквозным счётом (`03-domain-rules.md` §0).
Отсюда два вложенных автомата и два времени жизни состояния:

```
MatchState          живёт весь матч
├── счёт игроков    ← переносится между раздачами, растёт от навесов
├── scoreLimit      ← достижение = конец матча
├── dealNo
└── DealState       живёт одну раздачу
    ├── колода, козырь, руки, стол
    └── чей ход, кто пасовал
```

Практические следствия:

- Событийный `seq` — **сквозной по матчу**, а не по раздаче: клиент отслеживает один счётчик,
  и переход между раздачами не требует особой обработки при ресинке.
- Рейтинговое событие — завершение **матча**, а не раздачи.
- Снапшот пишется в том числе на границе раздач: там состояние компактно.
- Перемешивание каждой раздачи идёт от под-seed, выведенного из seed матча — весь матч,
  включая все перераздачи, остаётся воспроизводимым.

## Основные потоки

**Создание и старт матча**

```
логин (REST) → список столов (REST) → создать стол с card_set_id + theme_id (REST)
  → подключиться к столу (WS: TABLE_JOIN) → PLAYER_JOINED всем
  → все готовы (TABLE_READY) → сервер создаёт match, генерирует seed
  → MATCH_STARTED → DEAL_STARTED → CARDS_DEALT + STATE_SYNC каждому персонально
```

**Ход**

```
COMMAND (PLAY_CARD / PASS / TAKE / TRANSFER)
  → очередь стола → engine.apply → (newState, events)
  → запись в match_events → персональные EVENT всем участникам
  → перезапуск таймера хода
```

**Конец раздачи и перераздача**

```
карты кончились → DEAL_FINISHED (места, начисление очков навесами)
  → SCORE_CHANGED всем
  → достигнут scoreLimit?
       нет → новая раздача: под-seed, перемешивание, DEAL_STARTED
       да  → MATCH_OVER
```

**Завершение матча**

```
MATCH_OVER → в одной транзакции: matches.finished_at + loser + loss_type,
             match_players.place, пересчёт рейтинга, rating_history
  → событие MATCH_OVER всем + матч доступен в истории и реплее
```

**Отмена матча**

```
игрок не вернулся за 60 с → MATCH_ABORTED {reason}
  → matches.status = ABORTED, abort_reason
  → рейтинг НЕ трогаем, rating_history не пишем
  → матч виден в истории с пометкой «отменён», реплей доступен
```
