## Модули

| Модуль | Ответственность |
|---|---|
| `auth` | Регистрация, логин, JWT access/refresh, выдача WS-тикета |
| `user` | Профиль, отображаемое имя, аватар |
| `lobby` | Столы: создание, список, join/leave/ready, старт партии |
| `game.engine` | **Чистая игровая логика.** Состояние партии, команды, FSM, правила. Без Spring, БД и сети |
| `game.runtime` | Реестр активных столов, очередь команд на стол, таймеры хода, вызов engine, публикация событий |
| `game.ws` | WebSocket-хендлеры, разбор конвертов, персональные проекции состояния, рассылка |
| `history` | Персист лога событий, снапшоты, выдача истории и реплея |
| `rating` | Расчёт рейтинга по итогам партии, история рейтинга |
| `assets` | Наборы карт, темы стола, манифесты |

## Правило разделения REST и WS

| | REST | WebSocket |
|---|---|---|
| **Что** | Всё, что не является ходом в живой партии | Партия и live-события |
| **Примеры** | Регистрация, логин, профиль, список столов, создание стола, история партий, реплей, каталог наборов карт | Присоединение к столу, готовность, ход, взятие, перевод, синхронизация состояния, уведомление «твой ход» |
| **Модель** | Запрос → ответ | Команда → событие(я) всем участникам стола |

Граничный случай: **создание стола идёт по REST** (это не realtime-действие), а вход за стол —
по WS, потому что с него начинается подписка на события.

## Серверный авторитет

Единственный допустимый поток:

```
клиент → COMMAND (намерение) → сервер валидирует → engine применяет
                                       ↓
                        событие в лог + EVENT всем участникам
```

Клиент **никогда** не сообщает результат — только намерение. `GAME_DEFEND {cardId}` означает
«хочу отбиться этой картой», а не «я отбился». Решает сервер.

Список разрешённых действий сервер присылает вместе с состоянием (`availableActions`) —
чтобы фронт мог подсветить возможные ходы, не зная правил.

## Модель стола в рантайме ⭐

Ключевое решение. Стол — актороподобная сущность:

```
TableRuntime
├── tableId
├── состояние партии (в памяти, immutable, заменяется целиком)
├── очередь команд (MPSC)
├── один поток-обработчик (single-thread executor)
└── таймер текущего хода
```

Обработка команды:

1. Команда из WS попадает **в очередь**, а не выполняется на потоке WS-соединения.
2. Поток стола берёт команду, вызывает `engine.apply(state, command)` → `(newState, events)`.
3. События пишутся в `game_events` (append-only).
4. Для каждого участника строится **персональная проекция** и отправляется в его сокет.
5. Перезапускается таймер хода.

Почему так, а не блокировки вокруг разделяемого состояния: у стола 5 источников команд плюс
таймер, и каждая команда меняет состояние целиком. Очередь даёт линейный порядок бесплатно и
исключает целый класс гонок и дедлоков. Дополнительный бонус — движок может оставаться чисто
однопоточным и не думать о синхронизации вообще.

Реестр столов: `ConcurrentHashMap<TableId, TableRuntime>`. Пустые/завершённые столы выгружаются.

## Персональная проекция состояния (fog of war) ⭐

Внутреннее состояние содержит все карты всех игроков. Наружу оно **не сериализуется никогда**.

```
GameState (полное, только на сервере)
   ↓ project(state, forPlayer)
PlayerView: своя рука целиком, у остальных — только количество карт,
            размер колоды, козырь, стол, чья очередь, доступные действия
```

Проекция — обязательный слой, а не фильтр в сериализаторе. Правило: если DTO может физически
содержать чужую карту, он спроектирован неправильно.

## Восстановление и живучесть

| Сценарий | Поведение |
|---|---|
| Игрок потерял связь | Стол продолжает жить, ход игрока идёт по таймеру. Игрок переподключается → `RESYNC(last_seq)` → получает `STATE_SYNC` |
| Игрок закрыл вкладку надолго | Web Push «твой ход». Дальше — автодействие по таймауту. Политика выхода посреди партии — OQ-6 |
| Рестарт бэкенда | Стол пересоздаётся из `game_events` (+ последнего снапшота). Активные партии не теряются |
| Событие записалось, но не разослалось | Клиент обнаружит дыру в `seq` и запросит `RESYNC` |

Порядок «сначала записать событие, потом разослать» обязателен: разослать и упасть до записи —
значит рассинхронизировать клиентов с сервером навсегда.

## Путь к нескольким параллельным столам и инстансам

**Сейчас:** несколько столов на одном инстансе работают из коробки — реестр в памяти, у каждого
стола своя очередь и свой поток. Никаких дополнительных решений не требуется.

**Когда понадобится второй инстанс** (M8, не раньше):

- Sticky routing по `table_id` — все соединения одного стола попадают на один инстанс.
  Стол остаётся однопоточным, модель не меняется.
- Redis pub/sub — для событий, выходящих за пределы стола (presence, лобби, уведомления).
- Redis-блокировка на «владение» столом, чтобы два инстанса не подняли один стол из лога.

Что делаем уже сейчас, чтобы это осталось возможным:

1. Никакого состояния в HTTP-сессии — только JWT.
2. Всё состояние партии восстановимо из `game_events`.
3. `table_id` присутствует в каждом WS-сообщении — есть по чему маршрутизировать.
4. Лобби не держит состояние в памяти — читает из БД.

## Основные потоки

**Создание и старт партии**

```
логин (REST) → список столов (REST) → создать стол с card_set_id + theme_id (REST)
  → подключиться к столу (WS: TABLE_JOIN) → PLAYER_JOINED всем
  → все готовы (TABLE_READY) → сервер создаёт game, генерирует seed, раздаёт
  → CARDS_DEALT + STATE_SYNC каждому персонально
```

**Ход**

```
COMMAND (GAME_ATTACK/DEFEND/TRANSFER/TAKE/PASS)
  → очередь стола → engine.apply → (newState, events)
  → запись в game_events → персональные EVENT всем участникам
  → перезапуск таймера хода
```

**Завершение**

```
GAME_OVER → в одной транзакции: games.finished_at, game_players.place,
            пересчёт рейтинга, rating_history
  → событие GAME_OVER всем + партия доступна в истории и реплее
```
