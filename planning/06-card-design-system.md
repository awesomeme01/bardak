# 06 — Система дизайна карт и стола

## Задача

1. Хранить дизайн каждой карты и дизайн стола.
2. Иметь **несколько наборов** дизайна, выбираемых при создании стола.
3. Уметь **добавлять новые наборы** позже, без изменения кода.
4. Полноценный дизайн придёт позже — на MVP один набор-заглушка, но модель данных сразу
   мультинаборная.

## Главный принцип ⭐

**Логика карты и её изображение не связаны ничем, кроме кода карты.**

```
Движок знает:            Клиент рисует:
Card.Of(RANK_A, SPADES)  →  card_code "A-spades"  →  URL из манифеста выбранного набора
Card.Joker(1)            →  card_code "Joker-1"  →  общий Joker.png
```

Движок **никогда** не оперирует картинками, URL или наборами. Смена набора карт не может
повлиять на ход партии в принципе — это гарантия, а не соглашение.

## Коды карт и имена файлов ✅

Формат задан автором и **совпадает с именем файла без расширения** — один формат вместо двух,
никакого маппинга между «кодом в БД» и «файлом на диске»:

| Что | Код = имя файла | Примеры |
|---|---|---|
| Обычная карта | `<ранг>-<масть>` | `6-diamonds.png`, `10-hearts.png`, `A-spades.png`, `K-clubs.png` |
| Джокер | `Joker` | `Joker.png` |
| Рубашка | `back` | `back.png` |

- Ранги: `6 7 8 9 10 J Q K A`
- Масти: `diamonds` ♦, `hearts` ♥, `spades` ♠, `clubs` ♣
- Файлов в полном наборе: **36 карт + `Joker.png` + `back.png` = 38**

### Один файл джокера на несколько джокеров ⭐

Джокеров в колоде столько же, сколько игроков (до 5), но **картинка у них одна**. Логически
это разные карты, визуально — нет:

```
логическая карта  Joker-1 ┐
                  Joker-2 ├──→ Joker.png
                  Joker-3 ┘
```

Правило маппинга: код вида `Joker-<n>` рисуется файлом `Joker.png`. Если позже захочется
различать джокеров визуально, добавятся `Joker-1.png` и т.д., а правило станет «сначала
точное имя, иначе общий `Joker.png`» — коды карт при этом менять не придётся.

Коды **не меняются никогда** — на них завязаны манифесты всех наборов и весь исторический
лог событий.

## Модель данных

```
CardSet (набор карт)
├── code, name, description, version, preview_url
├── is_default, is_public, owner_user_id
└── CardAsset[]  ── card_code → asset_url + mime

TableTheme (тема стола)
├── code, name, preview_url
├── background_url        — фон/сукно
├── felt_color            — заливка, если фона нет
└── default_back_code     — какую рубашку брать по умолчанию

GameTable
├── card_set_id  ← выбирается при создании стола
└── theme_id     ← выбирается при создании стола
```

DDL — в `04-db-schema.md`.

Набор карт и тема стола разделены намеренно: хочется комбинировать «классические карты на
неоновом столе». Если окажется, что наборы всегда идут парой — свяжем позже, обратное
разделение сделать сложнее.

## Манифест набора

Набор = **манифест + ассеты**. Манифест отдаётся клиенту по
`GET /api/card-sets/{id}/manifest`:

```json
{
  "code": "classic",
  "name": "Классика",
  "version": "1.0.0",
  "format": "png",
  "cardSize": { "w": 500, "h": 726 },
  "cards": {
    "6-diamonds":  "/assets/card-sets/classic/6-diamonds.png",
    "6-hearts":    "/assets/card-sets/classic/6-hearts.png",
    "...":         "...",
    "A-clubs":     "/assets/card-sets/classic/A-clubs.png",
    "Joker":       "/assets/card-sets/classic/Joker.png",
    "back":        "/assets/card-sets/classic/back.png"
  }
}
```

**Валидация набора при регистрации** — набор считается валидным, только если покрывает:
- все 36 карт (`9 рангов × 4 масти`),
- `Joker`,
- `back`.

Неполный набор нельзя выбрать при создании стола. Проверка выполняется один раз при
регистрации набора, а не в рантайме на каждой раздаче.

## Хранение файлов

На MVP — статика, отдаваемая бэком из каталога:

```
back-bardak/assets/card-sets/<set-code>/
├── 6-diamonds.png   7-diamonds.png   …   A-diamonds.png
├── 6-hearts.png     7-hearts.png     …   A-hearts.png
├── 6-spades.png     7-spades.png     …   A-spades.png
├── 6-clubs.png      7-clubs.png      …   A-clubs.png
├── Joker.png
└── back.png

back-bardak/assets/themes/<theme-code>/background.jpg
```

Доступ через абстракцию:

```java
interface AssetStorage {
    String publicUrl(String key);
    void put(String key, InputStream data, String mime);
}
```

Реализация на MVP — `LocalFsAssetStorage`. Переезд на S3/MinIO = новая реализация того же
интерфейса, без изменений в домене. Смысл абстракции именно в этом: URL-ы ассетов хранятся
в БД, и если они окажутся жёстко привязаны к локальным путям, миграция превратится в
переписывание данных.

## Формат ассетов

Поддерживаются оба: поле `mime` в `card_assets` и `format` в манифесте для того и заведены.

- **PNG** — набор по умолчанию `classic`, 500×726 RGBA. Предсказуемый рендер, ничего не
  зависит от того, как браузер интерпретирует SVG.
- **SVG** — `classic-svg`, тот же дизайн вектором. Масштабируется без потерь и весит меньше
  на ретине, но сложные карты (фигуры) — это тяжёлые файлы с сотнями путей.

Пропорция карты **1 : 1.452** одинакова во всех наборах: клиент раскладывает карты по сетке
и не подгоняет размеры поштучно.

Клиент грузит **только манифест выбранного стола**, а не весь каталог. Ассеты кешируются
Service Worker'ом при входе за стол.

## Жизненный цикл

**Создание стола:**
```
GET /api/card-sets      → каталог с превью
GET /api/table-themes   → каталог тем
POST /api/tables {cardSetId, themeId, ...}
```

**Вход за стол:**
```
GET /api/tables/{id}                    → узнаём cardSetId
GET /api/card-sets/{id}/manifest        → манифест
предзагрузка ассетов + запись в Cache Storage (SW)
дальше рендер: cardCode → manifest.cards[cardCode]
```

**Важно:** набор фиксируется на столе, а не на игроке. Все за столом видят одни и те же карты —
иначе разговор «я скинул червовую даму» перестаёт работать. Персональные предпочтения
(например, своя рубашка) — возможное расширение, но не на MVP.

## Добавление нового набора

Целевой сценарий — **без единой строки кода**:

1. Положить ассеты в `assets/card-sets/<new-code>/`.
2. Зарегистрировать набор: `POST /api/admin/card-sets` с манифестом (или SQL-миграцией на MVP).
3. Сервер проверяет полноту покрытия карт.
4. Набор появляется в каталоге и доступен при создании стола.

Это работает ровно потому, что нигде в коде нет ни одного захардкоженного пути к картинке —
всё идёт через манифест.

## Что уже лежит в проекте ✅

Заглушки не понадобилось: набор по умолчанию — настоящий, импортирован из
public-domain набора vector-playing-cards (подробности и внесённые изменения —
`back-bardak/assets/card-sets/CREDITS.md`).

- `classic` — PNG 500×726, набор по умолчанию;
- `classic-svg` — тот же дизайн вектором.

Импортированы **все 52 карты**, хотя бардак играется 36-карточной колодой. OQ-1 закрыт
в пользу `36 + N` при любом числе игроков, но ранги `2…5` оставлены в наборе: размер колоды
живёт в `rules_config` (ADR-016), и если по живым партиям решим расширить её, ассеты
уже готовы.

Рубашки в исходном наборе не было — дорисована в его стиле (те же пропорции и скругление,
бордовая диагональная сетка). Джокер один на всех: `Joker-1` … `Joker-5` рисуются
общим `Joker.png`.

Когда придёт свой дизайн, он станет ещё одним набором рядом — менять придётся только
каталог ассетов и версию манифеста. Ни движок, ни БД, ни протокол не трогаются. Это и есть
проверка того, что разделение сделано правильно.

## Возможные расширения (не MVP)

- Пользовательские наборы: `owner_user_id` в `card_sets` уже заведён.
- Анимированные рубашки (Lottie/APNG).
- Наборы, привязанные к сезонам или достижениям.
- Персональная рубашка игрока поверх набора стола.
