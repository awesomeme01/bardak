# 01 — Карта знаний

Что нужно понимать, чтобы собрать этот проект. Приоритеты:

- 🔴 **нужно на MVP** — без этого не поедет
- 🟡 **нужно скоро** — на M4–M7
- 🟢 **позже** — когда появится нагрузка или второй инстанс

Отдельно помечено ⭐ — места, которые в этом проекте нетривиальны и где ошибка в понимании
стоит дороже всего.

---

## Бэкенд: Java

| Тема | Приоритет | Зачем именно здесь |
|---|---|---|
| `record`, immutability | 🔴 | Состояние игры и события — неизменяемые структуры. Мутабельное состояние в многопоточной игре = источник трудноуловимых багов |
| `sealed interface` + pattern matching | 🔴 ⭐ | Команды и события игры естественно ложатся на закрытую иерархию. Компилятор проверит, что обработаны все типы ходов — при добавлении «навесов» он сам покажет все места, которые надо дописать |
| Коллекции, `Optional`, Stream API | 🔴 | Повседневное |
| `ExecutorService`, `ScheduledExecutorService` | 🔴 ⭐ | Однопоточная очередь команд на стол + таймеры хода |
| `ConcurrentHashMap`, атомарность | 🔴 | Реестр активных столов |
| Virtual threads (Java 21) | 🟡 | Упрощают обработку WS-соединений, но не обязательны на старте |
| `SecureRandom` и seeded RNG | 🔴 ⭐ | Раздача карт должна быть честной, но воспроизводимой для реплея. Seed генерируется `SecureRandom`, сама раздача — детерминированным генератором от seed |

## Бэкенд: Spring

| Тема | Приоритет | Зачем |
|---|---|---|
| Spring Boot 3: автоконфигурация, профили, `application.yml` | 🔴 | База |
| Spring Web: контроллеры, `@RestControllerAdvice`, единый формат ошибок | 🔴 | REST-часть |
| Bean Validation (`@Valid`) | 🔴 | Валидация входа на границе |
| Spring Data JPA: репозитории, связи, `@Version` | 🔴 | Персист. Оптимистичная блокировка на столе и партии |
| Flyway | 🔴 | Миграции с первого коммита, не «сначала ddl-auto, потом разберёмся» |
| Spring Security: фильтры, `SecurityFilterChain`, `BCryptPasswordEncoder` | 🔴 | Авторизация |
| JWT: access/refresh, ротация, отзыв | 🔴 ⭐ | Свой велосипед тут легко сделать дырявым. Понимать: где хранить refresh, что делать при краже, зачем короткий access |
| **Авторизация WebSocket-соединения** | 🔴 ⭐ | Отдельная тема. Браузерный `WebSocket` не позволяет задать `Authorization` header — токен передаётся через subprotocol или одноразовый ticket. Классическая ошибка новичка: пустить WS без аутентификации, считая, что «за REST уже проверили» |
| Spring WebSocket: `WebSocketHandler`, сессии, рассылка группе | 🔴 | Транспорт партии |
| Backpressure и лимиты сообщений | 🟡 | Медленный клиент не должен подвешивать стол |
| Spring Actuator, Micrometer | 🟡 | Здоровье и метрики |
| Spring `@Scheduled` | 🟡 | Уборка мёртвых столов, истёкших токенов |

## Бэкенд: проектирование игры ⭐

Самая содержательная часть проекта. Это не «знание фреймворка», а способ мышления.

| Тема | Приоритет | Суть |
|---|---|---|
| **Конечный автомат (FSM)** | 🔴 | Игра — это состояние + переходы. Причём у нас их **два вложенных**: автомат матча (раздача → фиксация уровней навесов → перераздача → джокер) и автомат раздачи (`ATTACK → DEFEND → RESOLVE → REFILL → ...`). Явный автомат вместо россыпи `if` — единственный способ удержать правила бардака (строгий порядок подкидывания, пас, переводы, джокеры, навесы) в понятном виде |
| **Серверный авторитет** | 🔴 | Клиент присылает намерение, сервер решает. Даже «очевидные» проверки (моя ли очередь) — только на сервере |
| **Чистые функции над состоянием** | 🔴 | `apply(state, command) -> (newState, events)`. Без БД, без сети, без Spring. Тогда правила тестируются мгновенно и без поднятия приложения, а весь Spring-обвес становится тонким |
| **Детерминизм** | 🔴 | Одно и то же состояние + та же команда = тот же результат. Без этого невозможен реплей и невозможно воспроизвести баг из продакшена |
| **Персональная проекция состояния (fog of war)** | 🔴 ⭐ | Одно внутреннее состояние → N разных представлений, по одному на игрока. Чужие карты не сериализуются вообще, а не «сериализуются и прячутся» |
| **Event sourcing** | 🔴 | Партия хранится как последовательность событий. Отсюда бесплатно получаются: история, реплей, восстановление стола после рестарта, разбор спорных ситуаций |
| **Снапшоты** | 🟡 | Чтобы не проигрывать 300 событий при переподключении |
| **Идемпотентность команд** | 🔴 | Клиент переотправил команду после реконнекта — она не должна примениться дважды. Решается id команды + дедупликацией |
| **Sequence numbers и ресинк** | 🔴 | У каждого события — порядковый номер. Клиент после разрыва говорит «я на 42-м», сервер догоняет |
| **Модель конкурентности стола** | 🔴 ⭐ | Стол — актороподобная сущность: одна очередь, один поток-обработчик. Альтернатива (блокировки вокруг разделяемого состояния) на игре с 5 участниками и таймерами быстро превращается в дедлоки |
| **Таймеры хода** | 🔴 ⭐ | Ход 30 с с автодействием по таймауту; отключение игрока **останавливает** таймер (пауза матча), 60 с на возврат, иначе отмена. Приостанавливаемый таймер — не то же самое, что перезапускаемый: нужно уметь сохранять остаток |

## Бэкенд: инфраструктура

| Тема | Приоритет | Зачем |
|---|---|---|
| Docker, Docker Compose | 🔴 | Postgres локально, позже Redis |

## Фронтенд: JS

| Тема | Приоритет | Зачем |
|---|---|---|
| ES-модули, async/await, `fetch` | 🔴 | База |
| Vite: dev-сервер, сборка, proxy на бэк | 🔴 | Сборка |
| `WebSocket` API | 🔴 | Транспорт |
| **Reconnect с экспоненциальным backoff** | 🔴 ⭐ | Мобильный интернет рвётся постоянно. Наивный реконнект без backoff под нагрузкой устраивает себе DDoS |
| Heartbeat / ping-pong | 🔴 | Определить «соединение висит, но мертво» — таймауты TCP слишком длинные для игры |
| Очередь неотправленных команд | 🟡 | Ход, нажатый в момент разрыва, не должен теряться |
| Состояние клиента как проекция событий | 🔴 | Клиент не считает правила, только применяет то, что прислал сервер |

## Фронтенд: PWA

| Тема | Приоритет | Зачем |
|---|---|---|
| `manifest.json`, иконки, установка | 🟡 | Ярлык на домашнем экране |
| Service Worker: жизненный цикл, `install`/`activate`/`fetch` | 🟡 ⭐ | Самая контринтуитивная часть PWA. Особенно: обновление SW не должно рвать идущую партию |

| Web Push + VAPID (клиентская часть), Notifications API, права | 🟡 ⭐ | Уведомления в фоне идут **через Push, а не через WS** — закрытая вкладка означает закрытый сокет. Это регулярный источник непонимания |
| iOS-ограничения PWA | 🟡 | Push на iOS работает только для установленного на домашний экран приложения |

## Фронтенд: отрисовка стола

| Тема | Приоритет | Зачем |
|---|---|---|
| DOM + CSS transforms vs Canvas | 🔴 | Для карточной игры DOM достаточно и сильно проще: доступность, попадание по элементам, отладка. Canvas — только если упрёмся в производительность анимаций |

| FLIP-техника анимаций | 🟡 ⭐ | Карта «летит» из колоды в руку: анимируем перемещение между двумя позициями в разных контейнерах. Без FLIP это делается больно |
| Pointer Events, drag & drop, touch | 🟡 | Кинуть карту на стол пальцем |
| Раскладка 5 игроков вокруг стола, адаптив, safe-area | 🟡 | Портрет/ландшафт, вырезы на мобильных |
| SVG-спрайты и атласы, предзагрузка | 🟡 | 36+ карт разом |
| CSS-переменные для тем | 🟡 | Смена темы стола без пересборки |

## Что учить в первую очередь, если начинать с нуля

Порядок, в котором знания реально понадобятся по роадмапу:

1. Gradle + Spring Boot + Postgres + Flyway — поднять пустое приложение (M1).
2. Spring Security и JWT, включая авторизацию WS-handshake (M2).
3. Spring WebSocket и проектирование протокола (M2–M3).
4. FSM, чистые функции, детерминизм, персональные проекции — игровой движок (M4). **Основная
   интеллектуальная часть проекта, стоит потратить на неё больше всего времени.**
5. Event sourcing и реплей (M6).
6. Рейтинговые модели для N игроков (M6, см. `07-rating-system.md`).
7. Service Worker и Web Push (M7).
8. Redis и масштабирование (M8, только когда действительно понадобится).
