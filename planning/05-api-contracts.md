# 05 — Контракты API: REST и WebSocket

## Разделение

- **REST** — всё, что не является ходом в живом матче.
- **WebSocket** — матч и live-события.

Граница проведена в `02-architecture.md`. Практическое следствие: создание стола — REST,
вход за стол — WS.

Терминология: **матч** = игра в бардак до чьего-то джокера, **раздача** = партия дурака
внутри матча (см. `03-domain-rules.md` §0).

---

# REST

Базовый путь `/api`. Аутентификация — `Authorization: Bearer <access_token>`.

## Формат ошибок

Единый для всех эндпоинтов, отдаётся из `@RestControllerAdvice`:

```json
{
  "code": "TABLE_FULL",
  "message": "За столом нет свободных мест",
  "traceId": "b1f2...",
  "details": { "tableId": "..." }
}
```

`code` — машиночитаемый, стабильный. `message` — для человека, может меняться.

## Auth

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/auth/register` | `{username, displayName, password, email?}` → `{accessToken, refreshToken, user}` |
| `POST` | `/auth/login` | `{username, password}` → то же |
| `POST` | `/auth/refresh` | `{refreshToken}` → новая пара (с ротацией: старый отзывается) |
| `POST` | `/auth/logout` | Отзывает refresh-токен |
| `POST` | `/auth/ws-ticket` | ⭐ Одноразовый короткоживущий тикет для WS-handshake |

**Про `ws-ticket`.** Браузерный `WebSocket` не позволяет задать заголовок `Authorization`.
Варианты: токен в query (утекает в логи прокси и живёт часами), subprotocol (костыльно),
одноразовый тикет. Выбран тикет: клиент получает `{ticket, expiresIn: 30}`, открывает
`wss://.../ws?ticket=...`, тикет сгорает при использовании. Даже попав в лог, он бесполезен.
ADR-005.

|---|---|---|
| `GET` | `/tables` | Список открытых столов (`status=WAITING`) |
| `POST` | `/tables` | Создать: `{name, maxPlayers, cardSetId, themeId, rulesConfig, isPrivate}` |
| `GET` | `/tables/{id}` | Детали: игроки, набор карт, правила |

| `GET` | `/tables/invite/{code}` | ⭐ **Без токена.** Заглянуть за стол по ссылке-приглашению: название, сколько мест занято, можно ли сесть. Имён игроков в ответе нет — код живёт в переписке (ADR-063) |

## Matches / History

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/matches?userId=&status=` | История матчей: дата, участники, места, дельта рейтинга, отменённые с причиной и признаком `ratingCounted=false`. ⭐ Видна своя и **друга**; постороннему 403 `NOT_FRIENDS` |
| `GET` | `/matches/{id}` | Детали матча: итог + разбивка по раздачам. Виден участникам и друзьям любого из них |
| `GET` | `/matches/{id}/replay` | События матча для реплея |

⚠️ `/replay` доступен **только для завершённых или отменённых** матчей и отдаёт события через
ту же проекцию, что и live-игра. Отдать сырой `match_events` — значит раскрыть скрытую
информацию: по нему читаются чужие руки.

Отменённые матчи (`ABORTED`) в истории видны с причиной и пометкой «не влияет на рейтинг».

## Rating

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/rating/me` | Свой рейтинг и история точек для графика |
| `GET` | `/rating/users/{id}` | Рейтинг другого игрока |
| `GET` | `/rating/top` | Таблица по убыванию рейтинга |
| `GET` | `/rating/seasons` | `{seasons, canManage}` — сезоны новыми сверху и вправе ли спрашивающий закрыть текущий |
| `POST` | `/rating/seasons` | ⭐ Закрыть текущий сезон и открыть следующий: `{name}` |

Закрывать сезон вправе только логин из `bardak.rating.season-admins` (ADR-043); остальным —
`NOT_SEASON_ADMIN`. ⭐ Право едет вместе со списком (`canManage`), а не отдельной ручкой и
не флагом в профиле: оно живёт в настройках рейтинга, и знать о нём должен модуль рейтинга,
а не авторизация. Без признака экран показывал бы кнопку «закрыть сезон» всем, а отказ
прилетал бы уже после нажатия. Не игравший ни разу рейтинга в базе не имеет — ему отдаётся стартовое
значение и пустая история, а не ошибка.

## Push

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/push/key` | Открытый ключ VAPID: `{enabled, publicKey}` |
| `POST` | `/push/subscriptions` | Подписать устройство: `{endpoint, p256dh, auth}` |
| `DELETE` | `/push/subscriptions` | Отписать устройство: `{endpoint}` |

`enabled: false` — уведомления не настроены; клиент по этому признаку не показывает кнопку
подписки, а не показывает ошибку. Подписка принадлежит **устройству** (ADR-048): ключ —
`endpoint` от браузера, повторная подписка обновляет строку.

⭐ Уведомление уходит тому, из-за кого матч встал на паузу, и содержит время на возвращение
(ADR-047). Игроку за столом не уходит никогда.

## Friends ⭐

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/friends` | `{friends, incoming, outgoing}` — принятые, заявки ко мне, мои заявки |
| `POST` | `/friends/requests` | Позвать в друзья: `{username}` |
| `POST` | `/friends/{id}/accept` | Принять заявку |
| `DELETE` | `/friends/{id}` | Убрать из друзей **или** отклонить заявку |
| `POST` | `/friends/{id}/invite` | Позвать за стол: `{tableId}` → `{delivered}` |

Каждый друг приходит с `online` — считается по живому сокету, а не по «был недавно»
(ADR-054). Логин в `POST /friends/requests` ищется **без учёта регистра**, как и при входе
(ADR-058).

⭐ Убрать из друзей и отклонить заявку — одна операция: и то и другое означает, что пары
больше нет. Хранить отказы значило бы помнить, кому уже отказали, — это память не про игру.

⭐ Встречная заявка засчитывается как **согласие**, а не вторая заявка: иначе двое, нажавшие
«добавить» одновременно, остались бы с двумя висящими приглашениями и без дружбы.

`delivered` в ответе на приглашение — дошло ли **прямо сейчас** по сокету. Приглашение нигде
не хранится (ADR-055): не дошло — друга зовут push-ом, и экран честно пишет «его нет в сети».
Звать можно только друга: проверка на сервере, потому что запрос приходит из сети, а не
с экрана.

# WebSocket

Эндпоинт: `wss://host/ws?ticket=<one-time-ticket>`

## Транспорт: сырой WS + JSON, не STOMP

ADR-002. Причины:

1. Нужны **персональные проекции состояния** — каждому игроку своё сообщение со своими
   картами. Модель STOMP «топик → все подписчики получают одно и то же» работает против
   задачи; пришлось бы заводить топик на игрока, и выгода исчезает.
2. Собственный конверт даёт явное поле версии протокола.
3. Меньше абстракций между кодом и проводом.

Цена: heartbeat, ack, дедупликацию и переподключение пишем сами.

## Конверт

Одинаковый в обе стороны:

```json
{
  "v": 1,
  "id": "c-7f3a",
  "type": "PLAY_CARD",
  "tableId": "uuid",
  "seq": 42,
  "ts": 1730000000000,
  "payload": { }
}
```

| Поле | Смысл |
|---|---|
| `v` | Версия протокола. Несовпадение → `ERROR: PROTOCOL_VERSION_UNSUPPORTED` |
| `id` | Уникальный id сообщения. У команд — для идемпотентности и ack |
| `type` | Тип команды или события |
| `tableId` | Всегда присутствует — по нему маршрутизация к столу (и в будущем к инстансу) |
| `seq` | Только у событий: **сквозной номер по матчу**, не по раздаче |
| `payload` | Данные |

## Команды (client → server)

Намерения. Никогда не результаты.

| Тип | Payload | Смысл |
|---|---|---|
| `TABLE_JOIN` | `{}` | Сесть за стол |
| `TABLE_LEAVE` | `{}` | Встать из-за стола |
| `TABLE_READY` | `{ready}` | Готовность к старту матча |
| **`PLAY_CARD`** | `{cardCode, targetCardCode?}` | ⭐ Универсальное «положить карту на стол» |
| `PASS` | `{}` | «Больше не подкидываю» — передаёт право второму соседу |
| `TAKE` | `{}` | Взять карты со стола |
| `TRANSFER` | `{cardCode}` | Перевести атаку на следующего — карта **добавляется** в атаку |
| `ROLL_DICE` | `{}` | Бросок кости, когда козырем вышел джокер (§1.2 правил) |
| `CHOOSE_TRUMP` | `{suit}` | Победитель броска выбирает козырную масть |
| **`HANG_CARD`** | `{cardCode, targetSeat}` | ⭐ Навесить карту в слот соперника |
| `HANG_SKIP` | `{}` | Отказаться от навеса — право уходит дальше |
| `HANG_CLAIM` | `{cardCode}` | Заявка на навес в 5-секундном окне, когда право равно у нескольких |
| ~~`PLAY_JOKER`~~ | — | ✅ Отдельной команды не нужно: джокер играется обычными `PLAY_CARD` / `DEFEND` / `TRANSFER` (ADR-032) |
| `RESYNC` | `{lastSeq}` | Догнать состояние после разрыва |
| `PING` | `{}` | Heartbeat |

### `HANG_CARD` — навес ⭐

Доступна только в фазе `HANGING`, которая открывается **после «взял»** (не после «бито»)
и только тому, у кого сейчас право навесить: сначала последний атаковавший, затем остальные
(`03-domain-rules.md` §2.3).

Сервер проверяет:

| Проверка | Ошибка при нарушении |
|---|---|
| Фаза `HANGING` | `NOT_HANGING_PHASE` |
| Право навешивать сейчас у отправителя | `NOT_YOUR_TURN` |
| `targetSeat` — тот, кто только что взял | `INVALID_HANG_TARGET` |
| `targetSeat` ≠ отправитель | `CANNOT_HANG_ON_SELF` |
| Карта есть в руке | `CARD_NOT_IN_HAND` |
| **Ранг карты = следующий по шкале жертвы** | `WRONG_NAVES_RANK` |

Последняя проверка — суть механики: навесить можно только следующую ступень личной шкалы
(`6` → `7` → … → `A` → `Joker`), масть не важна.

### `PLAY_CARD` — одна команда, два смысла ⭐

Смысл зависит от роли отправителя, и сервер определяет её сам:

| Роль отправителя | `targetCardCode` | Что произойдёт |
|---|---|---|
| Атакующий / подкидывающий | отсутствует | Атака или подкид |
| Защищающийся | **обязателен** | Отбить именно эту атакующую карту |

Защищающийся обязан указывать цель. Это не UI-удобство: при нескольких атакующих картах на
столе иначе невозможно однозначно зафиксировать, что чем отбито. `PLAY_CARD` от
защищающегося без `targetCardCode` → `ERROR: TARGET_REQUIRED`.

### `MATCH_LEAVE` — выйти из идущего матча ⭐

Уйти посреди партии можно, но только явно и с последствиями для всех: матч отменяется
целиком, места освобождаются, стол снова открыт.

Отличается от пропажи со связи (§5.2) тем, что ждать некого: человек ушёл сознательно,
и держать остальных минуту на паузе незачем. Отменённый матч в рейтинг не идёт ни для кого
(§5.3) — уйти из проигранной партии, «чтобы не засчиталась», всё равно не выйдет.

⚠️ Тихо освободить своё место нельзя: движок продолжал бы ждать ушедшего, а на освободившийся
стул сел бы посторонний.

### `PASS` — явная фиксация отказа ⭐

Раунд не завершается «сам по себе». Обладатель права подкидывать обязан спасовать —
это и передаёт право второму соседу (следующему по часовой за защищающимся). Спасовавший
в этом раунде больше подкидывать не может.

### `ATTEMPT_REJECTED` — попытка неверного хода 🟨

Необязательная социальная фишка (флаг `showRejectedAttempts`, реализуется последней).
Когда защищающийся положил карту, которая не бьёт указанную цель:

- ход отклоняется, состояние не меняется;
- фронт **отправителя** откатывает действие сразу, не дожидаясь сервера — для отзывчивости;
- остальные получают `ATTEMPT_REJECTED {seatNo}` и рисуют мелькнувшую **рубашку**.

Payload содержит только номер места. Какая именно карта — не передаётся никому: иначе это
утечка скрытой информации. Сервер валидирует ход в любом случае — откат на фронте это
только скорость реакции, не источник истины (ADR-003).

### `TABLE_INVITE` — друг зовёт за стол ⭐

```json
{"type": "TABLE_INVITE", "payload": {
    "fromName": "Аня", "tableId": "…", "tableName": "Вечерний", "tableCode": "NBW67T"}}
```

Приходит **вне стола**: соединение открыто всё время, пока приложение открыто (ADR-053),
поэтому оклик слышно и в лобби, и в истории. Кода стола в сообщении достаточно, чтобы сесть
одним нажатием.

## Персональная проекция `STATE_SYNC` ⭐

```json
{
  "matchId": "uuid",
  "seq": 42,
  "matchStatus": "IN_PROGRESS",
  "dealNo": 3,
  "phase": "DEFEND",
  "trumpSuit": "H",
  "protectedSuit": "S",
  "deckLeft": 12,
  "iHaveHiddenCard": true,
  "discardCount": 20,
  "anyTrickBeaten": true,
  "maxAttackThisRound": 6,
  "myHand": ["A-spades", "7-hearts"],
  "mySeat": 2,
  "players": [
    {"seatNo": 0, "userId": "...", "displayName": "...", "cardsCount": 6,
     "hung": ["6-clubs"], "navesLevel": "6", "nextNavesRank": "7",
     "online": true, "passed": true},
    {"seatNo": 1, "userId": "...", "displayName": "...", "cardsCount": 4,
     "hung": [], "navesLevel": "K", "nextNavesRank": "A",
     "online": true, "passed": false}
  ],
  "table": [
    {"attack": "10-diamonds", "defend": null}
  ],
  "attackerSeat": 1,
  "defenderSeat": 2,
  "canAttackSeat": 1,
  "turnDeadlineTs": 1730000030000,
  "availableActions": [
    {"type": "PLAY_CARD", "cardCode": "7-hearts", "targetCardCode": "10-diamonds"},
    {"type": "TAKE"}
  ]
}
```

Четыре принципиальных момента:

0. ⭐ **Слот навесов открыт всем.** Три поля вместо одного, и все три нужны:
   - `hung` — карты, навешенные в **этой** раздаче; очищается при перераздаче;
   - `navesLevel` — достигнутый уровень шкалы; **переносится** между раздачами;
   - `nextNavesRank` — что можно навесить следующим; сервер считает сам, чтобы фронт не
     воспроизводил шкалу.

   Это единственные чужие карты, попадающие в проекцию, и попадают легально: «кому осталось
   два навеса до джокера» — ключевая информация за столом. После перераздачи `hung` пуст, а
   `navesLevel` остался — по нему фронт рисует placeholder в пустом слоте.
1. **Чужой руки в этом объекте нет физически.** Только `cardsCount`. Не «есть, но скрыты» —
   их нет в сериализованном виде вообще.

   ⭐ **Скрытая карта не попадает в проекцию вообще ни к кому — даже к владельцу.** В `myHand`
   её нет, у соседей — только флаг «есть/нет».

   ⭐ **При вскрытии её видит только владелец**: карта уходит к нему в руку и дальше
   играется как обычная. Событие о вскрытии **персональное** — соперникам уходит лишь
   изменившийся снимок: флага скрытой карты больше нет, `cardsCount` на единицу больше.
   Потайной козырь (§1.9) устроен наоборот: он вскрывается **всем**, с мастью и номиналом,
   потому что меняет козырь всему столу. Это единственная сущность в игре, которую
   не видит никто, пока она не откроется (`03-domain-rules.md` §1.8). Владелец знает лишь
   `iHaveHiddenCard: true`.

   `protectedSuit` шлётся отдельно от `trumpSuit`: козырь может смениться посреди раздачи
   (потайной козырь, §1.9), и защищённая масть пересчитывается вместе с ним — фронт не
   должен выводить её сам.
2. **`availableActions` приходит от сервера.** Фронт подсвечивает возможные ходы, не зная
   правил. В фазе `HANGING` там окажутся `HANG_CARD` с конкретными картами из руки и
   `HANG_SKIP` — фронт не вычисляет, какой ранг сейчас подходит.
3. **Положение по навесам видно всегда** — игрок должен в любой момент понимать, насколько он
   и соперники близки к джокеру. Это заменяет счёт, которого в бардаке нет.

`canAttackSeat` — у кого сейчас право подкидывать. Отдельно от `attackerSeat`, потому что
после паса право уходит второму соседу, а начавшим раунд остаётся прежний игрок.
Аналогично в фазе `HANGING` есть `canHangSeat`.

⭐ **Про отбой.** `discardCount` — сколько карт ушло в отбой, `anyTrickBeaten` — были ли уже
биты в этой раздаче. Второе определяет лимит атаки (5 в первом раунде, 6 дальше — §1.5
правил), поэтому сервер шлёт и готовый `maxAttackThisRound`, чтобы фронт не воспроизводил
правило.

Карты отбоя **не передаются** — только количество. Фронт рисует символическую стопку
перевёрнутых карт: игрок должен видеть, что биты были, но не что именно в них ушло.

## Навес: обмен сообщениями ⭐

```
защищающийся не отбился → TAKE
  → TRICK_RESOLVED {outcome: TAKEN}
  → HANGING_STARTED {targetSeat: 2, canHangSeat: 1, requiredRank: "7"}
        │
        ├─ у игрока 1 есть семёрка и он хочет:
        │     HANG_CARD {cardCode: "7-clubs", targetSeat: 2}
        │       → CARD_HUNG {fromSeat: 1, toSeat: 2, cardCode: "7-clubs",
        │                    navesLevelAfter: "7"}
        │
        ├─ не хочет или нечем:
        │     HANG_SKIP  → HANGING_SKIPPED {seatNo: 1, nextCanHangSeat: 3}
        │       → право уходит следующему, requiredRank тот же
        │
        └─ никто не навесил → фаза закрывается, идём в REFILL
```

`openToAll` в `HANGING_STARTED` поднимается, когда приоритет не действует: жертва —
отстающий (§2.3), навешивается джокер, или право дошло до «всех остальных». Тогда
`canHangSeat` не заполнен, окно длится **5 секунд**, и заявки шлются командой `HANG_CLAIM`.

Заявился один → он навешивает. Заявились несколько → **бросок кости** между ними
(`DICE_ROLL_REQUIRED` / `DICE_ROLLED`), победитель навешивает, у остальных карта остаётся
в руке (ADR-029).

Если навешен джокер, дополнительно приходит `JOKER_HUNG {seatNo}`. Это **не объявление
проигрыша**: игрок, вышедший первым в этой же раздаче, снимает джокер и продолжает играть
(`03-domain-rules.md` §0.4, corner case 1). Судьба решается только в `DEAL_FINISHED`.

## Итог раздачи: `DEAL_FINISHED` ⭐

Самое насыщенное событие протокола — в нём результат всех четырёх проходов подсчёта
(`03-domain-rules.md` §0.6):

```json
{
  "dealNo": 3,
  "dealLoserSeat": 2,
  "results": [
    {"seatNo": 0, "place": 1, "navesLevelBefore": "7", "navesLevelAfter": "6"},
    {"seatNo": 1, "place": 2, "navesLevelBefore": "A", "navesLevelAfter": "A"},
    {"seatNo": 2, "place": null, "navesLevelBefore": "K", "navesLevelAfter": "JK"}
  ],
  "levelChanges": [
    {"seatNo": 0, "reason": "FINISHED_FIRST", "delta": -1},
    {"seatNo": 2, "reason": "HUNG", "by": 1, "card": "A-clubs"},
    {"seatNo": 2, "reason": "LOST_DEAL", "delta": 1},
    {"seatNo": 1, "reason": "KILLED_LOSER", "delta": -1, "victim": 2}
  ],
  "losers": [{"seatNo": 2, "lossType": "SUPER_MEGA_FAIL"}]
}
```

`levelChanges` нужен, потому что уровень двигают четыре разные причины и они сочетаются.
Без разбора по причинам игрок не поймёт, почему его `−1` куда-то делся, а `KILLED_LOSER`
(награда за добивание чужого) вообще выглядит необъяснимо.

`losers` пустой → перераздача. Непустой → следом придёт `MATCH_OVER`; проигравших может быть
несколько, главный определяется старшинством степени.

## Пауза при отключении ⭐

```
клиент перестал отвечать
  → MATCH_PAUSED {reason: PLAYER_DISCONNECTED, waitingForSeat: 3, resumeDeadlineTs}
  → у всех останавливается таймер хода, показывается «Игрок 3 не может подключиться»
  → игрок вернулся  → MATCH_RESUMED, таймер хода продолжается С ОСТАТКА
  → не вернулся за disconnectGraceSeconds (60 с)
        → MATCH_ABORTED {reason: "Игрок 3 покинул игру"}
```

Таймер хода именно **приостанавливается**, а не тикает дальше: иначе за время разрыва у
игрока сгорит ход, и он вернётся уже наказанным за проблемы со связью.

## Переподключение и ресинк

```
разрыв → backoff (1s, 2s, 4s, 8s, макс 30s, с джиттером)
   → новый ws-ticket по REST
   → connect → TABLE_JOIN
   → RESYNC {lastSeq: 42}
       ├─ дыра небольшая → сервер досылает события 43..N
       └─ дыра большая / снапшот новее → полный STATE_SYNC
```

`seq` сквозной по матчу — клиент отслеживает один счётчик за всё время за столом, и переход
между раздачами не требует особой обработки при ресинке.

Клиент обязан:
- отслеживать `seq` и запрашивать `RESYNC` при обнаружении дыры;
- не применять события с `seq <= lastAppliedSeq` (защита от дублей);
- переотправлять неподтверждённые команды с тем же `id` — сервер дедуплицирует по `id`.

## Heartbeat

- Клиент шлёт `PING` каждые 20 сек, ждёт `PONG`.
- Нет `PONG` дважды подряд → соединение мертво, реконнект.
- Сервер, не получая активности, переводит матч в `PAUSED` и запускает
  `disconnectGraceSeconds`.

Нужно именно прикладное ping/pong: TCP-таймауты измеряются минутами, а у нас ход длится
30 секунд.

## Версионирование протокола

- `v` в конверте. Ломающее изменение → `v+1`.
- Сервер какое-то время поддерживает обе версии; клиент со старой `v` получает `ERROR`
  с `code = PROTOCOL_VERSION_UNSUPPORTED`.
- Новое **необязательное** поле или новый тип события версию не ломают — клиент обязан
  игнорировать неизвестные типы событий, а не падать.

## Лимиты и защита

- Rate limit на команды: не больше N в секунду с соединения.
- Максимальный размер сообщения ограничен.
- Любая команда проверяется на: мою ли очередь, за этим ли я столом, легален ли ход.
  Нелегальная команда → `ERROR`, состояние не меняется, соединение не рвётся.
