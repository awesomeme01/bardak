# 05 — Контракты API: REST и WebSocket

## Разделение

- **REST** — всё, что не является ходом в живой партии.
- **WebSocket** — партия и live-события.

Граница проведена в `02-architecture.md`. Практическое следствие: создание стола — REST,
вход за стол — WS.

---

# REST

Базовый путь `/api`. Аутентификация — `Authorization: Bearer <access_token>`.

## Формат ошибок

Единый для всех эндпоинтов, отдаётся из `@RestControllerAdvice`:

```json
{
  "code": "TABLE_FULL",
  "message": "За столом нет свободных мест",
  "traceId": "b1f2...",
  "details": { "tableId": "..." }
}
```

`code` — машиночитаемый, стабильный. `message` — для человека, может меняться.

## Auth

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/auth/register` | `{username, displayName, password, email?}` → `{accessToken, refreshToken, user}` |
| `POST` | `/auth/login` | `{username, password}` → то же |
| `POST` | `/auth/refresh` | `{refreshToken}` → новая пара (с ротацией: старый refresh отзывается) |
| `POST` | `/auth/logout` | Отзывает refresh-токен |
| `POST` | `/auth/ws-ticket` | ⭐ Выдаёт одноразовый короткоживущий тикет для WS-handshake |

**Про `ws-ticket`.** Браузерный `WebSocket` не позволяет задать заголовок `Authorization`.
Варианты: токен в query-параметре (утекает в логи прокси), в subprotocol (костыльно) или
одноразовый тикет. Выбран тикет: клиент по REST получает `{ticket, expiresIn: 30}`, затем
открывает `wss://.../ws?ticket=...`. Тикет живёт секунды и сгорает при использовании — даже
попав в лог, он бесполезен. Решение зафиксировано в ADR-005.

# WebSocket

Эндпоинт: `wss://host/ws?ticket=<one-time-ticket>`

## Транспорт: сырой WS + JSON, не STOMP

Решение зафиксировано в ADR-002. Причины:

1. Нам нужны **персональные проекции состояния** — каждому участнику стола уходит своё
   сообщение. Модель STOMP «подписка на топик = все получают одно и то же» здесь работает
   против нас: пришлось бы делать по топику на игрока, что сводит выгоду STOMP к нулю.
2. Собственный конверт даёт явное версионирование протокола.
3. Меньше магии — при отладке видно ровно то, что летит по проводу.

Цена: heartbeat, ack и переподключение пишем сами. Для одного проекта это дешевле, чем
бороться с абстракцией брокера.

## Конверт

Одинаковый в обе стороны:

```json
{
  "v": 1,
  "id": "c-7f3a",
  "type": "GAME_ATTACK",
  "tableId": "uuid",
  "seq": 42,
  "ts": 1730000000000,
  "payload": { }
}
```

| Поле | Смысл |
|---|---|
| `v` | Версия протокола. Несовпадение → сервер отвечает `ERROR: PROTOCOL_VERSION` |
| `id` | Уникальный id сообщения. У команд — для идемпотентности и ack |
| `type` | Тип команды или события |
| `tableId` | Всегда присутствует — по нему маршрутизация к столу (и в будущем к инстансу) |
| `seq` | Только у событий: порядковый номер в партии. По нему клиент видит дыры |
| `payload` | Данные |

## Команды (client → server)

Намерения. Никогда не результаты.

| Тип | Payload | Смысл |
|---|---|---|
| `TABLE_JOIN` | `{}` | Сесть за стол |
| `TABLE_LEAVE` | `{}` | Встать из-за стола |
| `TABLE_READY` | `{ready: bool}` | Готовность к старту |
| `GAME_ATTACK` | `{cardCode}` | Атаковать / подкинуть карту |
| `GAME_DEFEND` | `{cardCode, targetCardCode}` | Отбить конкретную атакующую карту |
| `GAME_TRANSFER` | `{cardCode}` | Перевести атаку на следующего |
| `GAME_TAKE` | `{}` | Взять карты со стола |
| `GAME_PASS` | `{}` | Отказаться от подкидывания («бито» с моей стороны) |
| `GAME_PLAY_JOKER` | `{jokerIndex, ...}` | 🟨 Payload зависит от правил джокеров (OQ-2) |
| `RESYNC` | `{lastSeq}` | Догнать состояние после разрыва |
| `PING` | `{}` | Heartbeat |

Зарезервировано: `GAME_NAVES_*` — под механику навесов (OQ-3).

## События (server → client)

| Тип | Payload | Кому |
|---|---|---|
| `STATE_SYNC` | Полная **персональная** проекция состояния | Одному игроку |
| `PLAYER_JOINED` / `PLAYER_LEFT` | `{userId, seatNo, displayName}` | Всем за столом |
| `PLAYER_READY` | `{userId, ready}` | Всем |
| `GAME_STARTED` | `{gameId, trumpSuit, seats[]}` | Всем |
| `CARDS_DEALT` | Свои карты; у остальных — только количество | Персонально |
| `TURN_CHANGED` | `{attackerSeat, defenderSeat, deadlineTs}` | Всем |
| `CARD_PLAYED` | `{seatNo, cardCode, slot, kind: ATTACK\|DEFEND\|TRANSFER}` | Всем |
| `TRICK_RESOLVED` | `{outcome: BEATEN\|TAKEN, nextAttackerSeat}` | Всем |
| `CARDS_DRAWN` | `{drawn: [{seatNo, count}], deckLeft}` + свои карты | Персонально |
| `PLAYER_OUT` | `{seatNo, place}` | Всем |
| `GAME_OVER` | `{places[], loserSeat, ratingChanges[]}` | Всем |
| `ACK` | `{commandId, accepted}` | Отправителю команды |
| `ERROR` | `{code, message, commandId?}` | Отправителю |
| `PONG` | `{}` | Отправителю |

## Персональная проекция `STATE_SYNC` ⭐

```json
{
  "gameId": "uuid",
  "seq": 42,
  "phase": "DEFEND",
  "trumpSuit": "H",
  "deckLeft": 12,
  "myHand": ["S_A", "H_7", "JOKER_1"],
  "mySeat": 2,
  "players": [
    {"seatNo": 0, "userId": "...", "displayName": "...", "cardsCount": 6, "online": true},
    {"seatNo": 1, "userId": "...", "displayName": "...", "cardsCount": 4, "online": true}
  ],
  "table": [
    {"attack": "D_10", "defend": null}
  ],
  "attackerSeat": 1,
  "defenderSeat": 2,
  "turnDeadlineTs": 1730000045000,
  "availableActions": [
    {"type": "GAME_DEFEND", "cardCode": "H_7", "targetCardCode": "D_10"},
    {"type": "GAME_TAKE"}
  ]
}
```

Два принципиальных момента:

1. **Чужих карт в этом объекте нет физически.** Только `cardsCount`. Не «есть, но скрыты» —
   их нет в сериализованном виде вообще.
2. **`availableActions` приходит от сервера.** Фронт подсвечивает возможные ходы, не зная
   правил. Когда добавим навесы, фронт не придётся переучивать — он просто получит новые
   типы действий в списке.

## Переподключение и ресинк

```
разрыв → backoff (1s, 2s, 4s, 8s, макс 30s, с джиттером)
   → новый ws-ticket по REST
   → connect → TABLE_JOIN
   → RESYNC {lastSeq: 42}
       ├─ дыра небольшая → сервер досылает события 43..N
       └─ дыра большая / снапшот новее → сервер шлёт полный STATE_SYNC
```

Клиент обязан:
- отслеживать `seq` и запрашивать `RESYNC` при обнаружении дыры;
- не применять события с `seq <= lastAppliedSeq` (защита от дублей);
- переотправлять неподтверждённые команды с тем же `id` — сервер дедуплицирует по `id`.

## Heartbeat

- Клиент шлёт `PING` каждые 20 сек, ждёт `PONG`.
- Нет `PONG` два раза подряд → соединение считается мёртвым, реконнект.
- Сервер закрывает сессию без активности дольше 60 сек.

Нужно именно прикладное ping/pong: TCP-таймауты измеряются минутами, для игры с таймером
хода это неприемлемо долго.

## Версионирование протокола

- `v` в конверте. Ломающее изменение → `v+1`.
- Сервер какое-то время поддерживает обе версии; клиент со старой `v` получает `ERROR`
  с `code = PROTOCOL_VERSION_UNSUPPORTED` и подсказкой обновиться.
- Добавление нового **необязательного** поля или нового типа события версию не ломает —
  клиент обязан игнорировать неизвестные типы событий, а не падать.

## Лимиты и защита

- Rate limit на команды: не больше N в секунду с соединения.
- Максимальный размер сообщения ограничен.
- Любая команда проверяется на: мою ли очередь, за этим ли я столом, легален ли ход.
  Нелегальная команда → `ERROR`, состояние не меняется, соединение не рвётся.
