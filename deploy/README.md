# Выкатка «Бардака» на сервер

Три контейнера: Postgres, приложение, Caddy с автосертификатом. Больше ничего не нужно —
Redis, второй инстанс и sticky routing отменены решением (ADR-061).

## Что нужно от машины

VPS с Ubuntu, **2 vCPU / 2 ГБ** (цель из требований), Docker с плагином compose и домен,
A-запись которого смотрит на сервер. HTTPS не украшение: без него не работают ни
push-уведомления, ни установка PWA на телефон.

## Первый запуск

```bash
cp deploy/.env.example deploy/.env      # заполнить: домен, пароль базы, JWT, код приглашения
deploy/deploy.sh                        # собрать и поднять на этой же машине
BARDAK_HOST=user@vps deploy/deploy.sh   # или собрать здесь и увезти образ на сервер
```

⚠️ Сервер **откажется стартовать** с секретами по умолчанию (`BARDAK_ENV=prod`): и JWT-ключ,
и код приглашения из примера лежат в открытом репозитории. Это не придирка, а отказ —
сервер с чужим секретом выглядит совершенно здоровым.

⭐ Схему базы приложение накатывает само (MD-006), в том числе на пустую. Java для этого
не нужна.

## ⚠️ `deploy/.env` живёт ТОЛЬКО на сервере

В репозитории его нет и быть не может — там секреты. Отсюда правило, которое стоило
одной аварии: **`.env` не должен попадать в rsync**. Синхронизация с `--delete` считает
его лишним файлом и удаляет вместе с паролем базы, ключом JWT и парой VAPID; пароль базы
при этом восстановить неоткуда — он задан при инициализации тома Postgres.

Спасает только то, что переменные видны в живых контейнерах:

```sh
docker inspect bardak-app-1 --format '{{range .Config.Env}}{{println .}}{{end}}'
docker inspect bardak-postgres-1 --format '{{range .Config.Env}}{{println .}}{{end}}'
```

⭐ Поэтому выкатывать надо `tools/ship.sh` — он исключает `.env` из синхронизации
и отказывается продолжать, если файла на сервере вдруг нет.

## Выкатка новой версии

`deploy/deploy.sh` собирает образ с тегом из git-хэша, поднимает его и **ждёт, пока
`/api/health` ответит `UP`**. Не ответил — печатает логи и выходит с ошибкой: «задеплоил»
должно означать «работает», а не «контейнер запустился».

## Откат

```bash
deploy/rollback.sh              # покажет доступные теги
deploy/rollback.sh a1b2c3d      # вернёт этот образ
```

⚠️ Откатывается **только приложение**. База не трогается: миграции идут вперёд, и старый
бинарник на новой схеме работает, а «откат схемы» превращает аварию в потерю данных.

## Бэкапы

```bash
deploy/backup.sh                          # дамп + отправка в S3, чистка старых
deploy/restore.sh drill backups/bardak-*.dump   # учебная тревога на копии
deploy/restore.sh apply backups/bardak-*.dump   # боевое восстановление
```

Крон на сервере:

```
15 4 * * * /home/user/bardak/deploy/backup.sh >> /var/log/bardak-backup.log 2>&1
```

⚠️ **Бэкап, который ни разу не восстанавливали, — это не бэкап, а надежда.** `drill`
поднимает дамп в отдельной базе, считает пользователей, матчи и раздачи и удаляет её за
собой. Он ничего не ломает — гонять его стоит регулярно, а не в день аварии.

⚠️ Без `BARDAK_BACKUP_BUCKET` копия остаётся только на сервере. От «уронил таблицу» это
спасает, от «потерял сервер» — нет.

## Прокси для Telegram

Рядом с игрой живёт MTProto-прокси (`mtg`, fake-TLS) — отдельный контейнер в профиле
`proxy`, поэтому `ship.sh` и обычный `up -d` его не трогают.

```bash
tools/proxy.sh           # поднять/обновить и напечатать ссылку tg://proxy?...
tools/proxy.sh root@93.171.232.185 rotate # новый секрет (все розданные ссылки перестанут работать)
tools/proxy.sh root@93.171.232.185 down   # остановить
```

- Порт — `MTG_PORT` (8443): 443 занят Caddy. Docker публикует порт мимо ufw.
- ⭐ Секрет выпущен на `MTG_DOMAIN`: кто постучится без секрета, получит настоящую игру
  с сертификатом Caddy. ⚠️ Домен обязан резолвиться в этот сервер — иначе прокси висит на
  таймаутах (так было с приостановленным `bardak.shabahost.space`).
- ⚠️ IP общий с игрой: заблокируют прокси — отвалится и игра.

## Наблюдение

- `/api/health` — статус и число накатанных миграций. По нему же бьёт HEALTHCHECK образа.
- `BARDAK_DIAGNOSTICS_ADDR=127.0.0.1:6060` включает pprof и `/debug/runtime`
  (goroutine, память, пул соединений). ⚠️ Только на localhost: профили показывают
  внутренности процесса целиком. Смотреть через `ssh -L 6060:127.0.0.1:6060 user@vps`.
- Логи: `docker compose -f deploy/compose.prod.yaml logs -f app` — JSON, с traceId,
  который игрок видит в сообщении об ошибке.

## Чего в этом пакете нет

- **CI.** Выкатка руками с ноутбука — осознанный выбор для игры на вечер (ADR-061).
- **Мониторинга и алертов.** Prometheus не заводим; смотреть — `/api/health` и логи.
- **Второго инстанса.** Присутствие игроков живёт в памяти узла: со вторым узлом друзья
  перестали бы видеть друг друга.

## ⚠️ Что НЕ проверено

Образ и связка написаны, но **ни разу не собраны и не подняты**: на машине, где это
делалось, Docker Desktop сломался целиком (демон отвечает 500, VM недоступна). Первый
запуск на настоящей VPS — это и есть первая проверка. Прежде чем звать людей играть,
пройти: сборка образа, `deploy.sh`, `/api/health`, регистрация, матч вдвоём, `backup.sh`
и `restore.sh drill`.
